1. **The MQTT session doesn't persist across restarts as intended.**
   `clean: false` is used in conjunction with a `clientId` that includes the PID. After a restart, the PID usually changes, so the application fails to pick up the previous session's queue. A stable subscriber identifier is needed. [subscriber.ts:42](../../src/mesh/ingest/subscriber.ts:42)

2. **Better Auth allows bypassing your custom API restrictions.**
   The entire `/v1/auth/*` route is accessible via the library's handler, including administrative methods. I verified this: an administrator can change their own role via `/v1/auth/admin/set-role`—getting a `200` response—even though your service forbids this. You should restrict externally accessible auth endpoints and test them individually. [server.ts:48](../../src/app/server.ts:48)

3. **Disabling a device does not close alerts triggered by user-defined rules.**
   I tested this scenario: alert is open → device is turned off → sweep runs → alert remains `open`. Only system alerts are closed; new readings from the disabled device are no longer accepted. This deviates from the spec. [evaluation/service.ts:92](../../src/alerts/evaluation/service.ts:92)

4. **An error in alert calculation could lead to a missed trigger.**
   Readings are saved, and then the evaluation process starts. If an exception occurs, only a log entry remains; there is no retry logic, and deduplication will discard any subsequent duplicate packet. A persistent flag for unprocessed readings and a retry mechanism are needed. This would require an architectural change. [ingest/service.ts:154](../../src/mesh/ingest/service.ts:154)

5. **Health status may appear normal even if the subscription fails.**
   MQTT is considered connected before the subscription is actually confirmed. Subscription errors are merely logged, while the state remains `connected`. It would be better to consider the ingest service ready only after a successful subscription. [subscriber.ts:48](../../src/mesh/ingest/subscriber.ts:48)

6. **Querying the latest battery level becomes increasingly expensive as history grows.**
   The SQLite execution plan confirmed a full table scan of `device_metrics` involving a correlated subquery. With indefinite data retention, this will eventually become a problem; furthermore, synchronous SQLite operations block both HTTP requests and the ingest process. It is better to fetch the latest record for each device individually using an index. [network/repo.ts:11](../../src/mesh/network/repo.ts:11)
