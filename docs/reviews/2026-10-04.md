# Mesh Fire Detection project audit — October 4, 2026

## Status and scope

This is a review record and proposed remediation backlog. Findings remain open
unless a later change supplies verification evidence. Recommendations are not
approved product or architecture decisions. Existing SPEC and ARCHITECTURE
documents remain authoritative; update them when a proposed decision is accepted.

The review examined the current working copies, including uncommitted changes,
across backend, web, the project's firmware integration, flasher, maps planning,
and blog integration. It included source inspection, local quality gates,
isolated database experiments, and browser checks of Home, Map, Connect, Firmware,
and Coverage, including a 390-pixel mobile viewport.

It was not an exhaustive audit of upstream Meshtastic, a production penetration
test, a field trial, or a fresh full firmware build. No hardware was flashed or
configured. Hardware-to-broker delivery and production proxy behavior were not
verified. Application source was not changed during the review.

## Evidence and priorities

- **Reproduced:** observed in a local browser or an isolated in-memory database.
- **Inspected:** supported by source or configuration; the deployment or hardware
  consequence still needs integration verification.
- **Recommendation:** an improvement proposal, not a confirmed defect.
- **P1:** address before relying on real alerts or the affected external service.
- **P2:** significant follow-up work, ordered behind correctness fixes.

Priorities describe engineering urgency, not a formal vulnerability score.
Finding IDs remain stable so tests, changes, and decisions can reference them.

## Proposed implementation order

1. Close alternate authorization paths; preserve alert trigger context and
   resolve rule alerts when devices are disabled (BE-01 through BE-03).
2. Decide measurement freshness and rule-edit semantics. Make failed evaluation
   recoverable without duplicating alerts (BE-04, BE-09).
3. Bind MQTT topic identity to envelope identity, stabilize subscriber sessions,
   and make subscription readiness visible (BE-06 through BE-08).
4. Fix invalid calculator input, malformed URL fragments, and USB history
   isolation (WEB-01 through WEB-03).
5. Reconcile firmware defaults, public presets, licenses, sample labels, and
   build-readiness claims (FW-01, WEB-05, WEB-06, WEB-13).
6. Implement one shared live network state and verify the complete sensor →
   mesh → gateway → broker → reading → alert → UI path (WEB-04, FW-04).
7. Improve query scaling, proxy limits, deploy recovery, mobile panels, blog
   publishing, and bundle loading. Start the maps milestone with measured inputs.

## Decisions still required

- Maximum permitted measurement gap for duration rules; behavior when data is
  stale; whether duration can elapse without a new reading.
- Alert behavior after a rule is disabled, deleted, retargeted, or edited.
- Trigger snapshots versus immutable rule revisions.
- Separate deduplication of readings and reception observations.
- Recovery mechanism and idempotency for failed alert evaluation.
- Actual gateway transport, publishing QoS, offline buffering, and tested TLS
  support. Keep the existing gateway decision authoritative until replaced.
- Sensor hardware baseline for field trials and maps calibration.
- Whether draft blog posts are intentionally public.
- Whether shared UI components may use native buttons and tables; this requires
  an explicit update to the web markup conventions.

Do not treat these proposals as already implemented. For each completed finding,
record the change reference, regression test or integration evidence, remaining
limitations, and any corresponding SPEC/ARCHITECTURE update.
