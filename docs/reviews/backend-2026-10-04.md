# Backend audit — October 4, 2026

All findings are open at this snapshot. See the [project audit](2026-10-04.md)
for scope, evidence definitions, validation results, and implementation order.
Source links are relative to this repository. Proposed changes that alter
decisions must update SPEC and ARCHITECTURE in the implementation change.

## BE-01 — P1: alternate admin endpoints bypass account safeguards

**Evidence: reproduced.** [server.ts](../../src/app/server.ts) exposes the Better
Auth wildcard handler; [auth.ts](../../src/shared/auth/auth.ts) enables the admin
plugin. The own-role safeguard in [users/service.ts](../../src/users/service.ts)
does not run through the plugin endpoint.

An authenticated administrator posted their own user ID and `role: user` to
`/v1/auth/admin/set-role`; the isolated request returned HTTP 200. This can remove
the last administrator's access. Other plugin operations need an endpoint audit;
their individual behavior was not reproduced.

**Proposal:** restrict externally reachable auth operations and enforce user
management through the application policy. Preserve required trusted server calls.
**Acceptance:** own-role/access changes are rejected through every public entry
point; ordinary sign-in/out and invite acceptance work; tests cover anonymous,
user, and admin callers on exposed plugin endpoints.

## BE-02 — P1: editing a rule rewrites historical alert meaning

**Evidence: reproduced.** [lifecycle/repo.ts](../../src/alerts/lifecycle/repo.ts)
joins an alert to the current `alert_rules.metric`. A temperature rule opened an
alert with value 70. Changing the rule metric to relative humidity made that same
alert return `environmentMetrics.relativeHumidity` with trigger value 70.

**Proposal:** retain immutable trigger context, using a snapshot or rule revision.
Include metric, comparison, threshold, and relevant timing parameters. Decide how
to represent existing alerts whose original conditions cannot be reconstructed.
**Acceptance:** edits never change the meaning of existing alerts; historical
context and events remain accessible after soft deletion; migration tests cover
legacy data without inventing missing history.

## BE-03 — P1: disabling a device leaves rule alerts unresolved

**Evidence: reproduced.** [evaluation/service.ts](../../src/alerts/evaluation/service.ts)
resolves disabled devices' system alerts only. Open a rule alert, disable the
device, and run the sweep: the rule alert remains open. Ingest then rejects new
readings, removing the usual condition-clearance path. SPEC already requires
resolution when a device is disabled.

**Proposal:** resolve every unfinished alert for the disabled device and write
its reason to alert events. **Acceptance:** both open and acknowledged rule and
system alerts resolve; history and ownership remain intact; repeated processing
does not add duplicate resolution events.

## BE-04 — P1: duration streaks span missing observations

**Evidence: reproduced; policy clarification required.**
[evaluation/repo.ts](../../src/alerts/evaluation/repo.ts) breaks a streak only at
a nonmatching reading. A ten-minute rule received 70, no data for seven days,
then 70 again, and opened an alert. Those observations do not establish continuous
exceedance during the gap.

**Proposal:** decide an allowed gap and unknown/stale behavior against real
telemetry intervals. Record the decision in SPEC before implementation.
**Acceptance:** tests cover gaps below, at, and above the boundary, device
outages, recovery, strict threshold equality, and the chosen timer semantics.

## BE-05 — P1: packet deduplication discards reception evidence

**Evidence: reproduced.** [ingest/service.ts](../../src/mesh/ingest/service.ts)
returns before storing direct-link observations for a duplicate. A relayed copy
followed by a direct copy of the same packet left the network with zero links,
despite direct SNR/RSSI metadata on the second copy.

**Proposal:** deduplicate sensor readings separately from reception observations.
This changes the documented whole-packet rejection behavior and needs a matching
SPEC/ARCHITECTURE update. **Acceptance:** either arrival order preserves direct
evidence; multiple gateways can contribute observations; readings and alert
evaluation remain single; repeated identical observations have bounded behavior.

## BE-06 — P1: persistent subscriber identity changes on restart

**Evidence: inspected.** [subscriber.ts](../../src/mesh/ingest/subscriber.ts) uses
`clean: false` with `clientId: mesh-backend-${process.pid}`. Process restarts
usually change the ID, so they cannot resume the previous broker session.
[MQTT.js documents](https://github.com/mqttjs/MQTT.js) session reuse by client ID.

**Proposal:** use a stable deployment-specific ID and verify reconnect/session
behavior with Mosquitto. A stable ID alone does not make QoS 0 publications
durable; see FW-02. **Acceptance:** publish supported QoS messages while the
subscriber is down, restart it, verify delivery and deduplication, and document
loss guarantees and session cleanup.

## BE-07 — P1: topic identity is not bound to envelope identity

**Evidence: inspected.** [subscriber.ts](../../src/mesh/ingest/subscriber.ts) uses
the topic for logging; [decode.ts](../../src/mesh/ingest/decode.ts) derives gateway
identity from the envelope. Topic ACLs and the application's gateway allowlist
therefore do not establish the same identity. Production exploitation was not tested.

**Proposal:** validate the expected topic shape and compare its gateway segment
to the decoded envelope before accepting data. **Acceptance:** mismatches,
malformed topics, unknown gateways, and disabled gateways are rejected even when
the sender is registered; legitimate gateway topics remain accepted.

## BE-08 — P1: health reports a connection without subscription readiness

**Evidence: inspected.** [subscriber.ts](../../src/mesh/ingest/subscriber.ts) sets
connected before subscription confirmation and only logs subscription errors.
[health/service.ts](../../src/health/service.ts) can consequently report success
while ingest is unavailable.

**Proposal:** distinguish connection from successful subscription. Consider
separate operational freshness for accepted packets and successful sweeps;
silence thresholds need a decision because a small mesh can be legitimately quiet.
**Acceptance:** connection, subscription rejection, reconnect, and recovery have
tested states; monitoring cannot classify subscription failure as ready.

## BE-09 — P1: failed rule evaluation has no durable retry

**Evidence: inspected and covered by the existing storage-survival test.**
[ingest/service.ts](../../src/mesh/ingest/service.ts) stores readings, then catches
and logs evaluation failures. Data survives, but no recovery obligation is stored.
A brief threshold excursion can therefore be absent from alert history.

**Proposal:** record pending evaluation transactionally, using SQLite if suitable,
then process it with retries and idempotency. This extends the current architecture.
**Acceptance:** an injected failure and process restart preserve pending work;
recovery evaluates original readings in a defined order; retries create no
duplicate alerts/events; queue health is observable.

## BE-10 — P2: rate limits use an unverified proxy address chain

**Evidence: inspected; deployment verification required.**
[Caddyfile](../../config/deploy/Caddyfile) does not configure trusted Cloudflare
proxies; [rateLimit.ts](../../src/shared/http/rateLimit.ts) chooses the final
forwarded address. Under the documented CDN path, visitors may share a Cloudflare
address as their limit key. See [Caddy's proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

**Proposal:** configure verified proxy trust and one consistent client-address
policy for application and auth limits. **Acceptance:** integration tests through
the real chain distinguish clients and prevent forged headers from controlling
the key, including requests that reach the origin directly.

## BE-11 — P2: latest battery lookup scans historical metrics

**Evidence: measured locally.** [network/repo.ts](../../src/mesh/network/repo.ts)
has an outer scan and a correlated lookup. SQLite reported `SCAN dm` on 300,000
synthetic rows; one query took approximately 66 ms on the review machine. This is
not a VPS benchmark. Synchronous SQLite work occupies the event loop, and
indefinite retention increases the query's cost.

**Proposal:** query indexed latest rows from the device list or maintain a current
state projection without deleting history. **Acceptance:** inspect query plans
and benchmark representative history sizes; preserve latest non-null semantics,
timestamp ties, and never-reported devices.

## BE-12 — P2: deployment recovery is manual and timing-sensitive

**Evidence: inspected.** [release.sh](../../config/deploy/release.sh) switches
the current symlink, restarts, waits three seconds, and makes one health request.
Failure does not automatically restore the previous release.

**Proposal:** bounded readiness retries and an explicit recovery policy that
accounts for database migration compatibility. **Acceptance:** exercise slow
startup, failed startup, failed health, and a migration-incompatible rollback in
a disposable deployment; record the recovery procedure and data-safety limits.

## Maintenance and regression coverage

Keep the feature layers, injected clock, transactional writes, and SQLite.
The review does not justify replacing this stack. Prioritize tests for transitions
and alternate entry points over additional ordinary CRUD tests.

The review's full check stopped on 14 ESLint errors, several involving stylistic
ternary/mutation rules. Reconcile the rules with the project's clarity-first
standard; restore the gate without unexplained suppressions. The audit does not
assign these existing failures to a particular uncommitted change.
